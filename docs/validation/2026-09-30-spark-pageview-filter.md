## 2. 첫 버전과 문제 (WP-233, MR !216)

JVM 에서 `en`·`en.m` 줄을 거르고 canonical 제목으로 후보와 broadcast semi-join, 살아남은
원본 줄에 파이썬 `parse_row`(정본)를 적용.

| 항목 | 값 |
| --- | --- |
| 정확성 | 1,776시간 **5,081,341행**, 기존 `filtered-v2` 와 `only_new=0 only_ref=0 diff=0` |
| 지역성 | 덤프 읽기 태스크 1,852개 **NODE_LOCAL 100%** |
| 시간 | **5시간 6분** |

🔴 1차 전체 실행은 broadcast 없이 semi-join 해 enwiki 전체 줄을 셔플 → 데이터 EC2

드러났다. 하루씩 broadcast 로 고쳐 재실행했다.

## 5. 같은 조건 비교 — 일주일 168파일 (07-19~25)

| --- | --- | --- | --- | --- |
| 단일 서버 `zcat \| grep \| aggregate`, 2프로세스 | 2 | 710.8 s | 0.90× | 524,711행 |
| 단일 서버, 4프로세스 | 4 | 640.0 s | 1.00× | 524,711행 |
| -233 원래 Spark (전체 실행 10.35 s/시간 환산) | 4 | 약 1,738 s | 0.37× | — |
| Spark `--mode jvm` (개선 ①) | 4 | 548.2 s | **1.17×** | 완전 일치 |

| Spark `--mode grep`, executor 1개 | 2 | 938.6 s | — | 완전 일치 |

3. ~~⚠️ 1대 → 2대 확장성(938.6 → 456.8 s, 2.05배)은 선형 확장의 근거로 쓰지 않는다 —
   executor 1개가 서비스 EC2(운영 서버)에 배정돼 운영 부하가 섞였다. 미측정.~~ → §5-1 에서

### 5-1. 공정한 1대/2대 확장성 (2026-09-30 04:42Z ~ 05:08Z)

서비스 EC2 Worker 를 `docker stop` 해 **Worker 1대(데이터 EC2)만** 남긴 상태에서 돌리고,
다시 켜 2대가 붙은 것(Master `ALIVE` 2)을 확인한 뒤 연달아 같은 조건으로 돌렸다. 클러스터에
다른 앱은 없었고, 서비스 EC2 LIVE 편집 스트림은 로컬 모드라 클러스터를 쓰지 않는다.

| 설정 (grep, 168파일) | 코어 | 처리 시간 | 정확성 |
| --- | --- | --- | --- |
| 단일 서버 `zcat \| grep \| aggregate` 2프로세스 (데이터 EC2) | 2 | 710.8 s | 524,711행 |
| **Spark Worker 1대 (데이터 EC2)** | 2 | **814.7 s** | 완전 일치 |
| **Spark Worker 2대** | 4 | **464.5 s** | 완전 일치 |
| (재현) Spark Worker 2대, §5 측정 | 4 | 456.8 s | 완전 일치 |

* **1대 → 2대 1.75배, 확장 효율 88%** (이상 2배 대비). 2대 값은 두 번 재서 1.7% 차이로 재현됐다
* **Spark 고정 비용**: 같은 서버·같은 2코어에서 Spark 가 단일 서버 멀티프로세스보다 **15% 느리다**
  (814.7 / 710.8) — 태스크 기동·JVM→파이썬 바이트 전달·parquet 쓰기. 1대로는 손해지만 2대로
  늘리면 그 비용을 넘어 단일 서버 4프로세스보다 1.40배 빠르다
* 88% 인 이유(추정): 서비스 EC2 Worker 는 운영(PostgreSQL·backend·LIVE)과 CPU 를 나눠 쓴다

⚠️ 09-23 replay 의 "시간당 5.3초(3프로세스)" 는 같은 서버에서 무거운 작업 셋이 동시에 돌던
값이라 기준선으로 쓰지 않았다. -233 MR 의 "기존 2.6시간" 비교도 같은 이유로 조건이 달랐다.

### 5-2. Worker 코어 수 (2026-09-30 05:16Z ~ 06:03Z)

데이터 EC2 Worker 만 임시 override 로 `--cores 4` 로 띄우고(서비스 EC2 는 운영이라 2코어 유지)
같은 168파일을 grep 모드로 쟀다. 끝나고 `docker compose up -d worker` 로 원래 2코어로 되돌려
두 Worker `ALIVE` 를 확인했다.

| 설정 | 코어 | 처리 시간 |
| --- | --- | --- |
| 1대 × 2코어 (§5-1) | 2 | 814.7 s |
| **1대 × 4코어** | 4 | **1,307.7 s — 60% 느림** |
| 2대 × (2+2) | 4 | 464.5 s |
| **2대 × (4+2)** | 6 | **586.7 s — 26% 느림** |
| 대조: 2대 × (2+2), 맨 마지막에 다시 | 4 | **465.4 s** |

모두 524,711행 완전 일치.

**코어를 늘리면 느려진다.** 원인 판정:

* **CPU 크레딧 소진이 아니다** — 02:15Z 부터 약 3.5시간 연속 부하 뒤 마지막에 원래 설정을 다시
  돌린 대조가 465.4 s 로 앞선 두 값(456.8 · 464.5)과 같다. 실행 중 두 서버 CPU steal(`%st`) 0%
* **과다 할당이다** — grep 모드 태스크 하나는 파이썬 + `zcat` + `grep`, CPU 를 쓰는 프로세스
  3개다. 데이터 EC2(4 vCPU)에는 NameNode·DataNode·Kafka·Spark Master·드라이버·producer 가 이미
  떠 있어, 4코어를 주면 CPU 를 원하는 프로세스가 12개를 넘어 경합·문맥 교환으로 오히려 느려진다.
  2코어 설정의 데이터 EC2 유휴 23~37%(vmstat) 는 파이프 대기이지 더 줄 수 있는 여유가 아니었다

→ **이 클러스터(서버당 4 vCPU, 데몬 공유)에서는 Worker 당 2코어가 최적이다.** 코어 수는 태스크당
실제 프로세스 수와 같은 서버의 데몬을 보고 정한다.
