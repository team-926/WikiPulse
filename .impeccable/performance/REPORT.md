# PulseMap 확대·축소 성능 진단

측정일: 2026-09-17. 이 문서는 수정 전 진단 기록이다. 아래 변형은 별도의 브라우저 페이지에만 적용한 원인 분리 실험이다. 이후 적용한 변경과 전후 결과는 [최적화 기록](OPTIMIZATION.md)을 참고한다.

## 결론

확대·축소 때 전체 지도를 다시 렌더링하고, 제목 및 문서 라벨의 크기·배치를 매 프레임 변경하는 구조가 최적화의 우선 대상이다. 브라우저의 Layout/스타일 계산 비중이 크므로 React 계산 캐시만 추가하는 것으로는 충분하지 않다. 제목의 블러 자체를 없애는 것은 우선순위가 낮다.

## 측정 조건과 한계

- 현재 작업 트리에서 `VITE_DATA_SOURCE=mock`으로 별도 production build 생성. 원래 환경 파일과 `frontend/dist`는 변경하지 않음.
- 로컬 Playwright headless Chromium, 1440×1000 전체화면, 모션 감소 해제, 스캔 기본 재생.
- 36개 클러스터, 문서 318개, 간선 282개, 지도 하위 DOM 4,082개, 스캔 대상 636개. 시작 화면과 경계가 일부라도 겹치는 클러스터는 9개.
- 중앙 포인터에서 동일한 휠 입력 24회, 확대/축소 교대, 입력 사이 85ms 대기, 끝에서 650ms 대기. 브라우저가 느려지면 입력 처리도 지연되어 전체 측정 시간은 달라진다.
- 각 비교 조건 2회. 1×는 CPU 추가 제한 없음, 4×는 CDP CPU 감속 스트레스 조건. 4× 값은 실제 기기 FPS로 해석하지 않는다.
- FPS는 requestAnimationFrame 간격으로 계산한 처리 빈도이며, 실제 디스플레이에 표시된 프레임이나 사용자 기기의 FPS를 직접 측정한 값은 아니다.
- 스타일/레이아웃 시간은 CDP Performance 카운터 차이. FPS 비교는 원인 탐색 자료이며 완성된 최적화의 성능 보장이 아니다. 각 개선 효과를 단순 합산할 수 없다.

## 결과

추가 CPU 제한 없는 동일 비교 묶음의 평균:

| 브라우저 실험 | rAF 빈도 | p95 프레임 간격 | 의미 |
| --- | ---: | ---: | --- |
| 현재 구현 | 28.86 fps | 58.30 ms | 확대·축소 지연 재현 |
| 시작 화면 밖 클러스터에 display:none | 34.97 fps | 49.95 ms | 화면 밖 표현 처리량 감소 가능성 |
| 문서 라벨 글자 크기만 고정 | 32.43 fps | 50.00 ms | 글자 크기 변경에 따른 레이아웃 비용 |
| 기존 버튼으로 스캔 일시정지 | 34.15 fps | 50.00 ms | 스캔과 줌의 동시 갱신 비용 |

별도의 기본 상태 2회는 평균 29.56fps로 유사했다. 약 5.62초 측정에서 Script 0.703초, Layout 2.558초, RecalcStyle 0.522초, 전체 Task 5.460초였다. Layout과 스타일 계산은 함께 약 3.08초로 Script 실행보다 컸다.

4× CPU 감속 조건 평균:

| 브라우저 실험 | rAF 빈도 |
| --- | ---: |
| 현재 구현 | 5.64 fps |
| 제목 블러만 제거 | 5.58 fps |
| 모든 CSS filter 제거 | 5.64 fps |
| 문서 foreignObject 라벨 숨김 | 7.49 fps |
| 스캔 일시정지 | 7.62 fps |

이 비교에서는 제목의 빛번짐/블러만 제거해도 유의미한 개선이 나타나지 않았다. 라벨 숨김과 스캔 정지는 원인 확인용이며 기능 제거 제안이 아니다. 화면 밖 숨김은 처음의 가시성만 사용한 제한된 실험으로, 실제 구현에는 현재 배율/이동과 여유 영역을 반영해야 한다.

## 반복 갱신 증거

별도의 계측 실행(Observer/CPU profiler 포함, 기본 측정과 분리)에서는 카메라 `data-zoom` 변경 132회와 DOM 속성 변경 130,823건이 기록됐다.

- 제목/제목 박스 관련: 96,048건.
- 문서 라벨 style: 17,075건.
- 스캔 대상 노드와 간선 style: 16,948건.
- 제목 박스의 glow/body/shine 3개 rect에서 x/y/width/height/rx 각각 4,752회 변경(36개 × 카메라 변경 132회).

속성 변경 건수는 CPU 시간 비중과 동일하지 않다. 다만 카메라만 변해도 정적인 제목의 치수와 문서 표현 전체를 반복 갱신한다는 것을 확인한다.

## 권장 구현 순서

### 1. 카메라 갱신과 지도 내용 분리, 제목은 그룹 transform으로 보정

- `frontend/src/pages/pulse/useMapCamera.js:74`: RAF마다 `setCamera(next)` 호출.
- `frontend/src/pages/pulse/PulseMap.jsx:235`: 매번 전체 클러스터/간선/노드 JSX와 문서 라벨을 계산.
- `frontend/src/pages/pulse/PulseMap.jsx:274`: 제목 박스 치수와 3개 rect 좌표, 텍스트 font-size/위치/줄 간격을 배율별로 변경.
- 카메라 transform을 독립적으로 갱신하고, 정적인 클러스터·노드·간선 컴포넌트 및 계산을 캐시한다. 제목 줄바꿈·문자폭·노드 Map·간선 연결 정보는 입력 변경 때만 계산한다.
- 제목은 기본 치수/글꼴을 유지한 채 클러스터 위 기준점에 고정한 그룹의 scale로 `(zoom / DEFAULT_ZOOM)^0.35` 표시 비율을 구현한다. 현재 디자인과 크기 변화 비율을 유지하면서 반복 속성 변경을 줄일 수 있다.
- 단순히 React state를 ref로 바꾸기만 하지 않는다. 매 프레임 동일한 width/font-size 등을 직접 수정하면 레이아웃 비용은 남는다.

### 2. 화면 밖 클러스터의 렌더링과 스캔 갱신 제외

- 초기에는 36개 중 9개 클러스터가 화면과 겹치지만 전부 렌더링/업데이트된다.
- 여유 영역을 둔 가시성 판정으로 화면 안에 들어올 클러스터만 렌더링한다. 빠른 줌·드래그에서 나타나는 지연이나 깜빡임을 피하도록 경계를 넉넉히 잡는다.
- 전체 활성 이슈 데이터, 목록, 선택 상태는 유지한다. 화면 안의 노드 제목을 생략하거나 NEW 전용 지도로 되돌리는 변경은 하지 않는다.
- 스캔 대상도 현재 렌더링 집합에 맞춰 등록/해제해 제거된 DOM 참조가 남지 않게 한다.

### 3. 문서 라벨 재배치 줄이기

- `frontend/src/pages/pulse/DocumentLabels.jsx:39`: 318개 SVG foreignObject 안에서 HTML 줄바꿈/말줄임을 사용.
- `frontend/src/pages/pulse/DocumentLabels.jsx:52`: 줌에 따라 font-size를 갱신.
- 기본 줄바꿈과 텍스트를 캐시하고, 연속 줌 중에는 scale로 반응시키는 구조를 검토한다. 실제 줄바꿈 재계산은 필요한 배율 경계 또는 줌이 안정된 시점에 한정한다.
- 최종 글자 크기, 노드 내부 배치, 말줄임, 전체 제목 callout을 유지하는지 따로 검증한다. 즉시 SVG text로 교체하면 기존 줄바꿈·말줄임 기능을 다시 구현해야 하므로 1차 수정으로 권하지 않는다.

### 4. 스캔 처리 범위 및 스케줄 통합

- `frontend/src/pages/pulse/useNeonScan.js:20`: 모든 노드/간선/제목 636개를 등록.
- `frontend/src/pages/pulse/useNeonScan.js:58`: 약 30fps로 전체 대상을 순회하며 일부 style 변경.
- 카메라와 스캔의 프레임 갱신 순서를 맞추고, 가시 영역 중 파동/잔광 범위에 해당하는 대상만 갱신한다. 현재 코드에 이미 있는 강도 변화 임계치와 정지/화면 밖 중단은 유지한다.
- 포인터 위치 변환의 DOM 읽기는 쓰기와 분리해 배치한다. `useMapCamera.js`의 wheel 처리에서 `getScreenCTM()`을 중복 읽는 부분은 정리할 수 있지만 이것만을 주원인으로 단정하지 않는다.

## 우선순위가 낮은 작업

- 제목 빛번짐이나 네온 색상 제거: filter 제거 실험에서 개선이 없었음.
- force layout을 Worker로 이전: `PulsePage.jsx`에서 scene은 filtered 입력에 대해 useMemo되며, 카메라 state는 PulseMap 내부에 있어 줌마다 d3 배치를 다시 돌리는 구조가 아님.
- API/네트워크 또는 초기 번들 분할: 현재 재현한 문제는 이미 데이터를 받은 뒤의 연속 확대·축소 구간. 이 진단에서는 우선 대상이 아님.
- 전체 Canvas/WebGL 이전: 수정 범위가 크므로 위의 DOM/카메라 개선 후 필요 여부를 판단.

## 다음 구현의 검증 기준

같은 데이터·화면·휠 입력으로 전후를 비교한다. 평균 프레임뿐 아니라 p95 지연, Layout/Style 시간, DOM 변경량이 함께 줄어야 한다. 포인터 고정 줌, 줌 경계/초기화, 일반·전체화면 전환, 모든 노드 제목, 제목의 완만한 스케일, 스캔과 제목 글로우의 위치 일치, 호 회전, 키보드/터치/모션 감소 동작을 유지한다.
